## Summary
Тексты и граф глав («Ветвящаяся история») нужно хранить так, чтобы агент-сценарист писал их как текст без редактора Godot, а граф проверялся чистым кодом без движка сцен. Решено: один JSON-файл на главу в `assets/data/heroes/<hero_id>/`, ключи латинским `snake_case`, условия строкой с минимальной грамматикой, загрузка в типизированные `RefCounted`-структуры чистым загрузчиком; граф проверяется отдельным валидатором (BS-01…BS-26) в тестах и CLI, не в релизной игре.

### Проверено по справке 4.7
- `FileAccess.store_*` возвращают `bool` (с 4.4): влияет на запись сохранений и инструмента `--freeze`, не на чтение данных; код записи обязан проверять возврат.
- Числа 64-битного диапазона через JSON теряют точность (`modules/random.md`): в данных глав таких чисел нет (только `schema_version`, `bonus` — малые целые); любое будущее 64-битное значение в JSON запрещено.

### Проверено в S1 на 4.7.2 (headless, gdUnit4), 2026-11-15
Закрывают строки таблицы ниже (кроме APK, времени/памяти и BOM/не-UTF-8). Источник — отчёт S1 и тесты `story_json_engine_test`.
- `JSON.new().parse(text)` при ошибке даёт `ERR_PARSE_ERROR`; `get_error_line()` **считает с нуля** — загрузчик прибавляет 1 для `DT-01`. `JSON.parse_string()` на битом тексте пишет в лог через `push_error` — запрещён.
- **Все JSON-числа — `float`**, включая `1`. Загрузчик приводит сам: целое = число без дробной части **и** `abs(n) <= 2^53` (иначе `DT-02`; `int(1e20)` недопустим). `load_from_dict` принимает и `int` (словари из кода), и целый `float`.
- **Дубль ключа в объекте: молча побеждает последний** — загрузчик не видит. **Висячая запятая (`[1, 2,]`, `{"a": 1,}`) парсер принимает** (мягче RFC 8259). Обе дыры закрывает только текстовый линтер CLI S5; в загрузчике не ловятся и не дублируются.
- Корень JSON может быть массивом (`parse` = OK) — `DT-02`.
- `FileAccess.open()` читает `res://` (в т. ч. `tests/fixtures/`) в gdUnit4 headless; на отсутствующем файле возвращает `null`, `get_open_error()` = `ERR_FILE_NOT_FOUND`, лог молчит.
- `Array[ClassName]` во вложенном `RefCounted`: `append()` / `append_array()` из нетипизированного массива работают, тип сохраняется.
- **`RegEx`: `$` совпадает перед завершающим `\n`** — `"s1\n"` проходит `^[a-z][a-z0-9_]*$`. Формат `id` проверять совпадением со **всей** строкой (`DictReader.is_id`).
- gdUnit4 останавливает сьют на первом упавшем тесте — счёт тестов в красном прогоне занижен.

## Context

### Problem Statement
GDD «Ветвящаяся история» определяет поля главы, сцены, варианта, исхода и перехода (Core Rules 2–7), 26 проверок данных BS-01…BS-26 и заморозку `id` (BS-26), но оставляет формат хранения ADR-у (Open Questions 1; отметка вставки в мосте, правило 6; разметка абзаца `говорит`/`урон`, строки 716–721; локализация — строка 217). Без формата нельзя ни писать главы, ни писать загрузчик и валидатор, ни фикстуры тестов.

### Constraints
- Один разработчик (CEO) и агенты; тексты пишут агенты-сценаристы без редактора Godot, то есть правят файлы как текст.
- Godot 4.7.2, GDScript со строгой типизацией (`lean-code`), Android, портрет.
- Проверка графа — чистым кодом, юнит-тесты gdUnit4 headless, без запуска игры и без сцен.
- Масштаб: ~12 сцен на главу в MVP, ~60 на героя, ~240 в полной версии. Объём главы 1500–2000 слов (BS-18).
- Локализация — Full Vision: тексты отдельно от структуры, `id` стабильны.
- Игровые значения не в коде; формат не должен требовать правки кода для новой главы.

### Requirements
- Должен выражать все поля GDD (в том числе `мост` с вставкой, `кода`, `старты`, `вехи`, `говорит`, `урон`, `исключение`, `устарел`).
- Должен давать читаемый git-diff на уровне абзаца/варианта.
- Должен отдавать ошибки данных кодами (BS-NN и коды загрузчика) с путём `глава/сцена/поле`, а не падением.
- Должен позволять заморозку и сверку `id` между выпусками.
- Игровая часть не должна зависеть от формата: только от типизированных структур.

## Decision

### 1. Носитель: JSON, один файл на главу; ключи латинским `snake_case`
- Файлы — UTF-8 без BOM, JSON (RFC 8259), отступ 2 пробела, один абзац на строку массива. Комментариев в JSON нет: поля, начинающиеся с `_` (например `_note`), загрузчик игнорирует — место для заметок сценариста.
- Кириллические ключи **не используются**: латинские ключи надёжнее для GDScript-кода (доступ `d["scenes"]`, без экранирования и без риска разной нормализации Unicode при правке разными агентами), они совпадают с уже принятым правилом `id` (`^[a-z][a-z0-9_]*$`, GDD правило 2) и `id` флагов (`run-state.md` правило 1). Русский остаётся в **значениях** (тексты, `title`, `reason`, `exception`).
- Перечисления в значениях тоже латинские (`risky`, не `рискованный`); русская форма существует только в GDD и в UI.
- Неизвестный ключ (не `_*`) — ошибка загрузчика `DT-04`: опечатка агента не должна молча терять поле.

**Форма `flags.json`** (читает `HeroLoader` в S3, не в S1): `{"schema_version": 1, "flags": [FlagDecl, ...]}`; ключи `FlagDecl` — строка «Флаг» таблицы выше.

Прочие правила формы:
- **Абзац** — либо строка (сокращение для `{"text": "..."}` без условия), либо объект `{text, if?, speaks?, damage?}`. Загрузчик нормализует оба вида в одну структуру. Список абзацев содержит хотя бы один безусловный (BS-06).
- **Вставка моста.** В `bridge.base` отметка места вставки — ровно один токен `{insert}`, если `inserts` непусты, и ни одного, если пусты (BS-06). Отметка — часть значения, не ключ.
- Русские кавычки «ёлочки» в текстах; ASCII `"` в тексте должен быть экранирован (иначе JSON не разберётся — `DT-01`).
- Все переводимые строки — листовые поля: `title`, `goal`, `text`, `reason`, `exception` (по правилу — не переводится, служебное), `bridge.base`, `inserts[].text`, `crit_*_line`, `milestones[].title` (если появится). Ключ перевода выводится из пути: `<hero>/<chapter>/<owner_id>/<поле>[/<индекс>]`.

### 2. Раскладка файлов
```
assets/data/
  heroes/
    <hero_id>/
      hero.json            # паспорт героя: stats, chapters (порядок), endings, portrait, accent
      flags.json           # объявления флагов героя (любой главы героя)
      chapters/
        <chapter_id>.json  # одна глава: starts, scenes, outcomes, transitions, milestones
      released_ids.json    # список выпущенных id (BS-26), генерируется при выпуске
```
- **Отличие от предложенного в задании `chapter_NN.json`:** имя файла — `<chapter_id>.json`. Порядок глав задаёт `hero.json → chapters`, а номер в имени файла дублировал бы порядок и ломался бы при перестановке; `id` главы заморожен (BS-26), значит имя файла стабильно.
- **Отличие: нет глобальных `assets/data/flags.json` и `assets/data/heroes.json`.** Флаг объявлен «в данных этого героя»; флаг другого героя для этого героя необъявлен (`run-state.md`, правило 1) — глобальный файл стёр бы границу героя. Реестр героев (перечень `hero_id` для меню) — отдельная малая структура, не часть этого ADR (при необходимости — `assets/data/hero_index.json` со списком `id`).
- **Одна глава — один файл** (~40–60 КБ при 1500–2000 словах, считано оценкой, не замером). Одна сцена — один файл отвергнута (см. Alternatives).
- **Длинные тексты** лежат внутри главы, листовыми строками, по одному абзацу на строку массива — отдельных файлов-текстов в MVP нет. Для локализации (Full Vision) инструмент извлекает строки по выведенным ключам в `chapters/<chapter_id>.<locale>.json` (плоская карта «ключ → строка»); загрузчик накладывает локаль поверх базовой. Эта надстройка не входит в MVP и не меняет формат главы.
- Фикстуры тестов — не в `assets/`, а в `tests/fixtures/story/` (раздел 6).

### 3. Версия схемы и заморозка `id`
- `schema_version` (int, сейчас `1`) — в каждом файле данных. Загрузчик принимает ровно одну версию; другая — `DT-07`, глава не загружается.
- Миграции — **офлайн**: скрипт в `tools/` переписывает файлы в одном коммите с повышением версии; рантайм-миграций нет (данные едут внутри APK и обновляются вместе с кодом). Сохранения хранят только `id` и в миграции формата данных не участвуют (ADR «Сохранения»).
- **Список выпущенных `id`** — `released_ids.json` на героя: `{schema_version, released_at, ids: {chapters, scenes, outcomes, transitions, endings, flags, starts}}`; `starts` — пары `<chapter_id>/<start_id>`. Файл создаёт и обновляет только CLI `tools/validate_data.gd --freeze` при выпуске и коммитит человек/Зам; сценаристы его не правят. Правило BS-26: `id`, который есть в списке, но пропал из данных, — ошибка сборки. Устаревшее убирается пометкой `deprecated: true`, не удалением (AC-26: сцена с пометкой — без находки). Новые `id` свободны; переименование = удаление старого + новый `id` = ошибка.

### 4. Загрузка и граница доверия
- **Чистый загрузчик** без `Node`, без `Engine`-синглтонов, без обращения к сцене: `ChapterLoader.load_from_dict(data: Dictionary, source: String) -> LoadResult` (чистая функция, тестируется без файлов) и тонкая обёртка `load_file(path: String) -> LoadResult`. `FileAccess` живёт **в одном месте — `ChapterLoader.read_object(path)`** (читает файл, парсит JSON, возвращает корневой объект или находку `DT-01`/`DT-02`); `load_file` и `HeroLoader` ходят в файлы только через него. `read_object`, `parse` (возвращает главу и при находках — нужна `HeroLoader` для проверок уровня героя) и `owned_ids` публичны лишь как контракт между двумя загрузчиками; остальной код их не зовёт. `LoadResult` — `RefCounted` (файл `load_result.gd`) с полями `data` (структура; **`null` при любой находке**) и `issues: Array[DataIssue]`.
- **Чтение JSON-объекта** — `DictReader` (`dict_reader.gd`): типизированные чтения ключей, `is_id`, `integer`. Целое: без дробной части и `abs(n) <= 2^53`, иначе `DT-02`; пустая обязательная строка — `DT-02`.
- **Коды отсутствия файла:** нет `hero.json` или файла главы как такового — `DT-01`; глава, перечисленная в `hero.chapters`, но без файла — `BS-01` (битая ссылка). Формат `id` — **`DT-06`** (не BS-01; «BS-01» в этом ADR относится только к ссылкам и уникальности).
- **Пространство `id`:** сцены, варианты, проверки, исходы и переходы героя — одно пространство (дубль между видами — `BS-01`); `starts` и `milestones` уникальны внутри главы.
- **`HeroLoader.load_hero(hero_id, root)`:** `hero_id` проверяется `is_id` (`DT-06`) до подстановки в путь; `hero.id` обязан равняться `hero_id` (`BS-01`).
- **Типизированные структуры** — `RefCounted` со статическими типами, не `Dictionary`: `HeroData`, `StatData` (`id`, `bonus`), `FlagDecl`, `ChapterData`, `StartData`, `SceneData`, `ParagraphData`, `OptionData`, `CheckData`, `OutcomeData`, `RouteData`, `TransitionData`, `BridgeData`, `MilestoneData`, `Condition` (AST), `DataIssue`. Причины: опечатка в имени поля ловится парсером GDScript, а не в рантайме; автодополнение для агентов-программистов; ядро не знает о JSON. `Dictionary` остаётся только внутри загрузчика.
- **Что проверяется где.**
  - Загрузчик, всегда (дёшево, ~десятки объектов): синтаксис JSON (`DT-01`), типы (`DT-02`), обязательные ключи (`DT-03`), неизвестные ключи (`DT-04`), значения перечислений (`DT-05`), формат `id` (`DT-06`), `schema_version` (`DT-07`), синтаксис условий (`DT-08`), и из BS — только ссылочная целостность BS-01 (ссылки существуют, `id` уникальны в данных героя, регулярное выражение `id`). Без этого структуры в памяти были бы недостоверны.
  - `GraphValidator` (BS-02…BS-26 + остаток BS-01 по флагам героя): только в тестах и в CLI `tools/validate_data.gd` (`godot --headless -s`), на всех главах всех героев; результат — `Array[DataIssue]` с кодом, строгостью (`error`/`warning`), путём `глава/сцена/поле` и `id`. Ошибка BS — красный CI; предупреждение — отчёт. В релизной игре граф-проверки не запускаются: данные уже прошли CI.
  - Рантайм: ошибка загрузчика на главе — глава не стартует, показывается служебный экран ошибки данных и пишется лог с кодом (в релизе данные CI-проверены, так что это страховка от порчи APK, а не рабочий путь). Тихого «по возможности продолжить» нет.
- **Все загрузки герой-уровня** (`hero.json`, `flags.json`) — в начале прохождения; главы — по требованию в момент входа в главу и освобождаются при уходе.

### 5. Язык условий (`если` / `условие`)
- **Строка внутри JSON** (ключ `if`), разбирает один класс `ConditionParser` при загрузке в AST `Condition`; вычисляет `Condition.evaluate(ctx: ConditionContext) -> bool`. Структурный JSON (`{"all": [...]}`) отвергнут: для агента-сценариста длинно и склонно к ошибкам скобок; строка читается в диффе как фраза.
- **Грамматика** (запросы Состояния, `run-state.md` правило 4 — есть, нет, любой из списка, любой флаг категории, какой стоит в группе; связки и/или/не; флаги не считаются):
```
expr    := or
or      := and { "or" and }
and     := not { "and" not }
not     := "not" not | atom
atom    := "(" expr ")" | flag_id
         | "any(" flag_id { "," flag_id } ")"        # любой из списка
         | "cat(" category ")"                        # любой флаг категории
         | "group(" group_id ")" "==" flag_id         # какой флаг стоит в группе
```
  - Скобки **нужны** для смешения: `a and b or c` без скобок — ошибка `DT-08` (сценарист обязан явно написать `(a and b) or c`). Только `and`-цепочка или только `or`-цепочка без скобок допустимы. Приоритет `not` > `and` > `or` задан, но неявной он не используется.
  - Токены — строчные латинские `and`, `or`, `not`; `flag_id` — по `^[a-z][a-z0-9_]*$`. Пустая строка `if` — ошибка (отсутствие условия = отсутствие ключа).
  - Не читаются журнал, броски, прошлые исходы, арифметика (Core Rules п. 7, 13).
- **Разрешение** `flag_id`/`group_id`/`category` против объявлений героя — после разбора, в загрузчике героя (BS-01); `ConditionContext` — интерфейс из трёх методов (`has_flag`, `any_in_category`, `flag_in_group`), его реализует `RunState`, а в тестах — `FakeFlags`.

**Уточнения после истории S2 (2026-11-15).** Пределы парсера: глубина скобок и `not` — 32 (`MAX_DEPTH`), длина условия — 1000 символов (`MAX_LENGTH`); превышение — `DT-08`. Пробел, таб, `\r` и `\n` — разделители; любой другой недопустимый символ — `DT-08` с кодом символа (U+XXXX). Неизвестное имя — одна `BS-01` на имя (первое вхождение). Слова `and`, `or`, `not`, `any`, `cat`, `group` не могут быть `id` флага, категории или группы (проверяет загрузчик флагов, S3). Пустая строка `if` — `DT-08` (отсутствие условия = отсутствие ключа). Подключение разбора `if` к `ChapterLoader` и проверка «флаг не из названной группы» — история S3. Файлы модуля: `condition.gd`, `condition_parser.gd`, `condition_context.gd` (интерфейс), `condition_vocabulary.gd` (известные имена). Движок 4.7.2: типизированный `Dictionary[String, String]` принимается (проверено компилятором).

Порядок написания по TDD — «План первых историй» в конце. Зависимости направлены одним способом: `data` ← `validation`, `data` ← `story_navigator`, `RunState` ← `story_navigator`; `data` ничего не знает о `RunState` (только об интерфейсе `ConditionContext`).

### Key Interfaces
- `ChapterLoader.load_from_dict(data: Dictionary, source: String) -> LoadResult` ; `load_file(path: String) -> LoadResult`
- `HeroLoader.load_hero(hero_id: String) -> LoadResult` (герой + флаги + главы)
- `ConditionParser.parse(text: String, known: ConditionVocabulary) -> ParseResult` ; `Condition.evaluate(ctx: ConditionContext) -> bool`
- `ConditionContext`: `has_flag(id: String) -> bool`, `any_in_category(category: String) -> bool`, `flag_in_group(group: String) -> String`
- `DataValidator.validate(hero: HeroData, options: ValidatorOptions) -> Array[DataIssue]` (`GraphValidator` S4 + смысловые проверки S5; `options` — переключатель строгости BS-25 и пределы F1–F8 из внешней конфигурации, не из кода; `ValidatorOptions.from_dict(config, source, issues)` и `load_file(path, issues)` — загрузчики опций)
- `ReleasedIds.read(raw: Dictionary, path: String, issues: Array[DataIssue]) -> ReleasedIds.Snapshot` (загрузчик: сырой `Dictionary` принимается только здесь; `Snapshot` — RefCounted: `released_at: String`, `ids: Dictionary[String, PackedStringArray]`)
- `ReleasedIds.compare(hero: HeroData, snapshot: ReleasedIds.Snapshot, path: String) -> Array[DataIssue]` (BS-26; CLI вызывает `read` + `compare`)
- `ReleasedIds.diff(hero: HeroData, released: Dictionary) -> Array[DataIssue]` (обёртка `read` + `compare` для тестов; CLI её не вызывает)
- `DataIssue`: `code: String` (`BS-NN` или `DT-NN`), `severity`, `path: String`, `object_id: String`, `message: String`

### Implementation Guidelines
- Загрузчик, парсер условий, валидатор и `story_navigator` **must** быть чистыми классами: без `Node`, `SceneTree`, автозагрузок и глобального состояния; `FileAccess` — только в `ChapterLoader.read_object` (чтение файла) и `HeroLoader` (`file_exists` перед чтением глав; справкой движка не покрыт, закреплён headless-тестом, на APK не проверен), `hero_loader`, `ValidatorOptions.load_file` (через `ChapterLoader.read_object`) и CLI `tools/validate_data.gd`, который читает и пишет `released_ids.json`; `ReleasedIds` файлов не касается. Остальные классы `validation/` файлов не читают.
- Структуры данных **must** иметь статические типы всех полей. Сырой `Dictionary` допускается только на входе загрузчиков (`ChapterLoader`, `HeroLoader`, `ValidatorOptions.from_dict`, `ReleasedIds.read`) и **must not** передаваться в валидаторы и `compare`: за границу загрузчика выходят типизированные объекты (`HeroData`, `ValidatorOptions`, `ReleasedIds.Snapshot`). Единственное исключение — тестовая обёртка `ReleasedIds.diff`.
- Ошибка данных **must** оформляться как `DataIssue` с кодом из таблицы BS/DT; `assert`/`push_error`-падение вместо находки — **must never**.
- Пределы F1–F8, `OPTIONS_MAX`, `P_EARLY_MAX` и т.п. **must** читаться из внешней конфигурации (`Gameplay values must be data-driven`), не быть константами в проверках.
- Поля, которых нет в таблице соответствия, **must never** добавляться в файлы без правки этого ADR (или его редакции и `schema_version`).
- Сценарист **must** править только `chapters/<chapter_id>.json` (и `flags.json` по поручению); `released_ids.json` — только CLI.
- Перед коммитом данных **must** запускаться `tools/validate_data.gd`; ошибка BS блокирует CI (`.claude/docs/coding-standards.md`, CI/CD Rules).
- `Condition` и ссылки на `id` **must** разрешаться при загрузке, а не при каждом показе сцены; условия вычисляются в моменты из Core Rules п. 7 (вход в сцену, после исхода, начало главы).

## Alternatives Considered

### Alternative 1: `.tres` / custom `Resource`
- **Description**: Классы `ChapterRes`, `SceneRes` с `@export`-полями; главы — `.tres`-файлы, загрузка `ResourceLoader`.
- **Pros**: встроенная типизация и импорт; редактор Godot показывает данные.
- **Cons**: агент пишет `.tres` как текст с `[sub_resource id=…]`, `ExtResource`, `uid` — хрупко, диффы шумные, длинные тексты в экранированных строках; проверка графа тянет `ResourceLoader` и сам движок в юнит-тесты; формат Godot меняется между версиями (мы на 4.7, справка 4.5–4.7 после отсечки модели, а правила `.tres` в `docs/engine-reference/` не описаны — NOT SOURCEABLE); локализацию и внешний инструмент придётся строить поверх.
- **Rejection Reason**: нарушает главное требование — текст без редактора и проверка без движка сцен.

### Alternative 2: Собственный текстовый формат (Ink-подобный/markdown с метаданными)
- **Description**: Сценарист пишет прозу с разметкой выборов; собственный парсер.
- **Pros**: лучший авторский опыт, самые чистые диффы.
- **Cons**: свой парсер и своя спецификация для одного разработчика; ошибки разметки — отдельный класс багов; граф всё равно нужно держать структурой; два формата (авторский и внутренний) — удвоенная поддержка.
- **Rejection Reason**: объём работ не окупается при ~12 сценах MVP. **Не закрывает дверь:** благодаря типизированным структурам и `load_from_dict` такой формат можно добавить позже как компилятор в тот же JSON, не меняя ядро.

### Alternative 3: JSON, одна сцена — один файл
- **Description**: ~240 файлов в полной версии, главы — каталоги.
- **Pros**: меньше конфликтов слияния при параллельной правке разными агентами.
- **Cons**: ссылки между файлами, порядок загрузки, больше ошибок «файл не найден»; графовые проверки BS-03/04/05/10 всё равно работают на главе целиком; агенту трудно видеть главу целиком; больше I/O на Android.
- **Rejection Reason**: одна глава — один писатель (по плану работ); выигрыш в слиянии не нужен, проигрыш в обзоре — реален.

### Alternative 4: Кириллические ключи JSON
- **Description**: ключи как в GDD (`"сцены"`, `"варианты"`, `"если"`).
- **Pros**: прямое соответствие GDD.
- **Cons**: доступ в GDScript через строковые литералы с кириллицей; риск смешения похожих символов (латинская `a`/кириллическая `а`) и разной нормализации Unicode у разных агентов — тихие ошибки данных; несовместимость с `id` и флагами (они латинские по GDD).
- **Rejection Reason**: латинские ключи + таблица соответствия дают то же понимание без этих рисков.

### Alternative 5: Условия структурой JSON
- **Description**: `{"all": ["a", {"not": "b"}]}`.
- **Pros**: не нужен парсер строк.
- **Cons**: многословно, глубокие вложенности, трудно читать в диффе и править агенту без редактора.
- **Rejection Reason**: парсер ~100 строк с полным тестовым покрытием дешевле, чем постоянные ошибки скобок в данных.

## Consequences

### Positive
- Агент пишет и правит главу как текст; диффы построчные.
- Вся логика данных и графа тестируется без движка сцен (через `load_from_dict`); фикстуры — маленькие словари/файлы.
- Игровой код зависит от типизированных структур, а не от формата: замена носителя — правка только загрузчика.
- BS-26 закрыт механически (список выпущенных `id` + CLI).
- Путь к локализации не требует перестройки формата.

### Negative
- Два слоя: JSON-словарь в загрузчике и типизированные структуры — код маппинга пишется руками (~1 класс на структуру).
- JSON без комментариев и без проверки дублей ключей; часть ошибок ловит только линтер CLI.
- Условия — строка со своей грамматикой: нужен парсер и тесты, переименование флага требует поиска по строкам (CLI должен давать «переименование флага» как проверку, но выпущенные флаги и так заморожены).
- Строгий отказ на неизвестный ключ делает добавление поля в схему согласованным изменением кода, ADR и данных.

## Performance Implications
- **CPU**: разбор одной главы (~12 сцен) на устройстве не замерен; ожидается пренебрежимо мало по сравнению с кадром, но это гипотеза — замер в S1/первой сборке. Разбор — вне кадрового цикла (при входе в главу).
- **Memory**: одна глава в памяти за раз; порядок — сотни КБ структур (оценка, не замер).
- **Load Time**: герой-уровень (`hero.json`, `flags.json`) — при выборе героя, главы — при входе.
- **Network**: нет.

## Migration Plan
Кода и данных в репозитории по этому формату ещё нет (`docs/architecture/` содержит только `tr-registry.yaml`). Миграции нет. Первая глава MVP пишется сразу по этому формату; прототипы в `prototypes/` не переносятся.

## Validation Criteria
- AC-01…AC-27 `branching-story.md` проходят на фикстурах; `ch_f1` даёт 0 ошибок и 0 предупреждений по BS-01…BS-19 (AC-27).
- Все строки таблицы NOT SOURCEABLE закрыты тестами или записями о проверке на APK.
- Сценарист-агент пишет главу, и `tools/validate_data.gd` принимает её без правок кода ядра.
- Первая экспортированная сборка читает данные героя на устройстве.
- Пересмотр решения, если: (а) разбор главы на среднем устройстве превышает бюджет кадра на загрузке заметно для игрока; (б) локализация показывает, что инлайн-тексты неприемлемы; (в) агенты стабильно ошибаются в синтаксисе условий — тогда авторский формат (Alternative 2) как компилятор в этот JSON.

## Risks
- **Хрупкость JSON для агентов** (запятые, кавычки). Митигация: `DT-01` со строкой; форматтер/линтер в CLI; запрет ASCII `"` в тексте, «ёлочки».
- **Дубли ключей и недоступные проверки загрузки на APK** (NOT SOURCEABLE). Митигация: текстовый линтер в S5; первая сборка на устройство — до наполнения глав.
- **Список полей паспорта героя и крит-фраз не сверен полностью** (в сессии не прочитаны все строки `heroes.md` п. 1 и `d20-checks.md` п. 1). Митигация: сверка в S1, отклонения — правкой таблицы этого ADR.
- **Разрастание грамматики условий.** Митигация: любое расширение — только правкой этого ADR и `run-state.md`.
- **Внешние зависимости не готовы**: реестр персонажей и каталог кадров (OQ 2) нужны BS-20; фикстуры подменяют их до готовности.
- **Список `id` портится человеком.** Митигация: файл генерирует только CLI; правка вручную — по ревью.

## План первых историй

Порядок — по зависимостям. Для каждой: тесты в `tests/unit/...`, фикстуры в `tests/fixtures/story/`; гейт — «Logic» (BLOCKING), автотест.

1. **S1. Структуры данных и загрузчик** (`src/core/story/data/`, кроме условий). Написать `DataIssue`, структуры, `ChapterLoader.load_from_dict/load_file`, `HeroLoader`; коды `DT-01…DT-07`; ссылочная целостность BS-01 (кроме условий и флагов). Закрывает: AC-01 (кроме ссылок на флаги и условий), в том числе проверку `id` `^[a-z][a-z0-9_]*$` (`Scene1`, `1a` — ошибка). Тесты: `ch_f1` загружается без находок; битый JSON → `DT-01` со строкой; неизвестный ключ → `DT-04`; `schema_version` ≠ 1 → `DT-07`; целочисленность `bonus` и `schema_version`; чтение фикстуры из файла в headless (закрывает NOT SOURCEABLE по `FileAccess` в gdUnit4); `m_refs` частично.
2. **S2. Язык условий** (`condition.gd`, `condition_parser.gd`). Грамматика раздела 5, ошибки `DT-08`, вычисление над `ConditionContext` (с `FakeFlags`). Закрывает: Core Rules п. 7; BS-01 для ссылок условий на флаги (AC-01, 6-й и 7-й случаи); основа для BS-11 (AC-11) и BS-12. Тесты: каждый вид атома; приоритет; запрет смешения `and`/`or` без скобок; пустая строка; неизвестный флаг/категория/группа.
3. **S3. Состояние флагов** (`src/core/state/run_state.gd`, `flag_decl`). Объявления героя, `ставит`/`снимает`, группы вытеснения, область `chapter`/`run`, необъявленный флаг — ошибка, `блокирует`; реализует `ConditionContext`. Закрывает: `run-state.md`, правила 1, 3, 4 и их AC (точные номера AC взять в `run-state.md` при разборке истории); `branching-story.md` AC-19 (категория/область `флаг_провала_цели`) — частично. Тесты: группа снимает остальные; снятие `chapter` в конце главы; повторная постановка идемпотентна.
4. **S4. Граф и структурные проверки** (`story_graph.gd`, `graph_validator.gd`, `checks/bs_structure.gd`). Индексы, рёбра, циклы, достижимость, тупики, форма главы. Закрывает: BS-02…BS-06, BS-09, BS-10 — AC-02, AC-03, AC-04, AC-05, AC-06, AC-09, AC-10; часть AC-27 (мутации BS-02, BS-05, BS-10). Тесты: `m_variant`, `m_deadend`, `m_reach`, `m_cycle`, `m_struct`, `m_shape`; `ch_f1` без находок.
5. **S5. Смысловые проверки, `id`-заморозка и CLI** (`checks/bs_traces.gd`, `bs_budget.gd`, `bs_ids.gd`, `released_ids.gd`, `tools/validate_data.gd`). Следы вариантов, ритм, бюджеты, ранняя смерть, слова на путь, иллюстрации (на фикстурах каталога), заголовки узловых, BS-26 и `--freeze`; текстовый линтер дублей ключей. Закрывает: AC-07, AC-08, AC-11…AC-25 (по номерам, где проверка не отложена GDD), AC-26 (список `id`), AC-27 целиком. Тесты: `m_trace`, `m_traces`, `m_early`, `m_words`, `ch_f1` (11/12 сцен, W 1790/1970); интеграционный `tests/integration/story/` — валидатор на настоящих данных героя.
6. **S6. Позиция и навигатор** (`story_position.gd`, `story_navigator.gd`). Выбор `старты` по флагам `run`; вход в сцену (условные абзацы, мост с одной вставкой — один раз при входе); выбор перехода сверху вниз по флагам после исхода; кода; точка возобновления `{глава, сцена, переход входа, ожидающий исход}`; возврат по снимку без ребра графа. Закрывает: Core Rules п. 3, 6, 7, 8, 10, 11; блоки AC «Показ, выбор перехода, исход», «Точка возобновления…», «Провал цели и следующая глава», «Финалы 3+1, коды» (номера — по блокам GDD). Принимает `CheckData`, бонус характеристики героя из `HeroData`, внедряемый RNG; возвращает результат и `id` исхода `success`/`failure`, фразу крита первой строкой. Закрывает: `d20-checks.md`, правила 1, 8, 9 (применение исхода один раз — через навигатор); формула шанса для F5/F6 из GDD (по `d20-checks.md` формула 2). Каждая история перед закрытием проходит `godot-mobile-auditor` (и `chaos-monkey` для S6) по правилам Hot-Reload Review Gate; в отчёте — `commands.test`.
